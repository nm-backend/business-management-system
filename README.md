# SkladPro.Nod — Product Requirements & Business Specification

> **SkladPro.Nod** — SaaS-система для управления камнеобрабатывающим бизнесом: заказы, склад, производство, сотрудники, клиенты, платежи, расходы и аналитика.
>
> Главный приоритет системы — **точность бизнес-расчётов, сохранность данных, безопасность и простота использования**. Интерфейс должен быть понятен человеку без технического опыта.

---

## 1. Общая концепция

SkladPro.Nod работает как **multi-tenant SaaS**.

Каждая компания является отдельным tenant и имеет полностью изолированные данные.

Компания A никогда не должна иметь возможность получить или изменить данные компании B.

Изоляция должна обеспечиваться не только интерфейсом, но и на уровне:

* API;
* permissions;
* serializers;
* ORM/querysets;
* database constraints;
* WebSocket;
* exports;
* media files.

### Архитектурный принцип

```text
Пользователь
    ↓
Аутентификация
    ↓
Роль
    ↓
Компания
    ↓
Permissions
    ↓
API
    ↓
Business Logic
    ↓
Database
```

Нельзя полагаться только на скрытие элементов интерфейса.

# 4. Ролевая модель

1. **Owner / Egasi**
2. **Admin / Administrator**
3. **Worker / Ishchi**

Также на уровне SaaS существует:

# 11. Остатки и потребность

Не путать:

```text
quantity
required_for_orders
available_quantity
shortage_quantity
```

### Значения

`quantity` — физический остаток.

`required_for_orders` — сколько товара требуется существующим заказам.

`shortage_quantity`:

```text
max(required_for_orders - quantity, 0)
```

`available_quantity` должно иметь однозначный бизнес-смысл.

Система обязана явно показывать:

```text
Физически есть
Требуется по заказам
Доступно
Нехватка
```

Нельзя скрывать нехватку через неправильную интерпретацию `reserved`.

# 12. Производство

Производство работает **только через подтверждение**.

Основной процесс:

```text
Task
 ↓
WorkRecord
 ↓
Awaiting confirmation
 ↓
Admin/Owner confirmation
 ↓
Material consumption
 ↓
Finished product
 ↓
Labor accrual
 ↓
Order update
```

### Работник

Указывает:

* товар;
* годное количество;
* брак;
* единицу;
* фото;
* комментарий.

### Подтверждение

После подтверждения программа:

1. проверяет рецепт;
2. проверяет наличие сырья;
3. списывает сырьё;
4. создаёт StockMovement;
5. добавляет годную продукцию;
6. пересчитывает себестоимость;
7. начисляет труд;
8. обновляет Task;
9. обновляет Order;
10. создаёт audit event;
11. отправляет уведомления.

Всё должно выполняться атомарно.

### Брак

Семантика должна быть однозначной:

```text
good_quantity = годная продукция
defect_quantity = брак
total_processed = good_quantity + defect_quantity
```

Материал расходуется на:

```text
good + defect
```

Годная продукция:

```text
finished_stock += good
```

Брак не должен попадать в готовый склад.

Оплата труда по умолчанию рассчитывается по годному количеству, если бизнес-правила не предусматривают другое.

# 22. Weighted Average Cost

Для входящих партий:

```text
new_avg =
(old_qty × old_avg + new_qty × new_price)
/
(old_qty + new_qty)
```

Пересчёт должен выполняться атомарно.

После изменения WAC исторические продажи не должны изменять уже зафиксированный COGS.

---

# 23. COGS

COGS должен использовать историческую себестоимость в момент выдачи/продажи.

Пример:

```text
Цена себестоимости при продаже = 50
```

Позже:

```text
WAC = 80
```

Старая продажа продолжает использовать:

```text
COGS = 50 × quantity
```

а не 80.

# 24. Конкурентность

Все критические операции должны быть защищены от race conditions.

Проверять через PostgreSQL:

### Payment

```text
Order = 1000

600 + 600 concurrently
```

Нельзя получить:

```text
paid = 1200
```

### Delivery

```text
Stock = 10

6 + 6 concurrently
```

Нельзя физически выдать 12.

### Confirmation

Один WorkRecord не должен быть подтверждён дважды параллельными запросами.

### Reservation

Не должно быть физически невозможного состояния склада.

### Worker payouts

Нельзя выплатить больше начисленного.

---

# 25. Idempotency

Повтор одного запроса после timeout/retry не должен создавать двойной бизнес-эффект.

Особенно:

* payments;
* delivery;
* production confirmation;
* reservations;
* worker payouts;
* subscription renewal;
* payment webhooks.

---

# 26. Subscription SaaS

Lifecycle:

```text
ACTIVE
   ↓
GRACE
   ↓
EXPIRED
   ↓
FROZEN
   ↓
RENEWED
   ↓
ACTIVE
```

### Grace

В grace бизнес продолжает работать.

Пользователь должен видеть предупреждение с датой окончания grace.

### Frozen

Бизнес-операции блокируются.

Но:

* login;
* profile;
* subscription;
* renewal

должны оставаться доступны.

### Source of truth

Должен существовать один authoritative subscription lifecycle.

`billing` может быть projection/invoice layer, но не должен конфликтовать с Company lifecycle.

Нельзя получить:

```text
Company = GRACE
billing = FROZEN
```

---

# 27. Tenant Security

Для Company A:

```text
Company A token
+
Company B object ID
```

должен быть заблокирован.

Проверять:

* clients;
* orders;
* payments;
* warehouse;
* production;
* finance;
* reports;
* messages;
* audit;
* subscriptions;
* media;
* WebSocket.

Запрещено доверять:

```text
company_id
```

из пользовательского request body.

---

# 28. RBAC и server-side data filtering

Финансовые поля должны быть исключены на уровне backend.

Например Admin НЕ получает:

```text
profit
cash
cost_price
purchase_price
salary_amount
client_payment_amount
debt_amount
```

Даже если frontend полностью изменён вручную.

# 30. Удаление данных

Критические записи не должны удаляться без необходимости.

Для исторических сущностей предпочтительны:

```text
archive
cancel
soft delete
immutable records
```

Особенно защищать:

* Payment;
* Expense;
* WorkerPayment;
* StockMovement;
* AuditLog;
* исторические заказы;
* исторические production records.

Финансовая история не должна исчезать обычным DELETE.

# 31. API Error Handling

Ошибки должны быть:

* конкретными;
* понятными;
* безопасными;
* локализуемыми.

Плохо:

```text
Invalid operation
```

Лучше:

```text
Недостаточно сырья: требуется 20 м², доступно 12 м².
```

Плохо:

```text
Bad Request
```

Лучше:

```text
Нельзя оплатить 700 сом: остаток долга составляет 300 сом.
```

Критические ошибки не должны превращаться в HTTP 500, если это ожидаемая validation/business ошибка.

# 32. UI/UX

Интерфейс должен быть понятен пользователю без технических знаний.

Основные принципы:

* минимум лишних действий;
* понятные кнопки;
* понятные статусы;
* очевидные предупреждения;
* важные действия на видном месте;
* финансовые данные визуально отделены;
* красный цвет используется для реальной проблемы;
* подтверждение опасных действий;
* отсутствие дублирующих настроек.

### Главное правило UX

Пользователь должен понимать:

```text
Что происходит?
Что нужно сделать?
Что будет после нажатия?
Почему действие недоступно?
```

# 37. Database Integrity

Критические бизнес-инварианты должны по возможности защищаться на уровне PostgreSQL.

Проверять:

* CHECK constraints;
* UNIQUE constraints;
* FK;
* indexes;
* decimal fields;
* delete behavior;
* nullability.

Особенно:

```text
quantity >= 0
required_for_orders >= 0
```

и остальные реальные инварианты системы.

# 41. Главный принцип SkladPro

SkladPro — не просто CRUD-приложение.

Это SaaS ERP, где ошибка в одной цифре может означать неправильную прибыль, долг, остаток склада или выплату сотруднику.

Поэтому приоритет разработки:

```text
1. Correctness
2. Financial accuracy
3. Data integrity
4. Tenant isolation
5. Security
6. Concurrency
7. Subscription consistency
8. API correctness
9. UX
10. Visual polish
```

**Backend и точность расчётов — основа продукта.**

Каждый критический бизнес-процесс должен быть:

```text
понятным
+
атомарным
+
безопасным
+
проверяемым
+
математически корректным
+
защищённым от повторного выполнения.
```
