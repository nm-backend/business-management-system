# План доработки SkladPro.Nod по 13 пунктам аудита

Источник: `docs/mockup-screen-audit-2026-09-08.md` (48 окон, 9 уникальных листов).
Ничего не реализуется «под макет»: у каждого пункта проверена бизнес-семантика,
и там, где макет спорит с текстом ТЗ, решение вынесено отдельно.

Обозначения ролей: **E** — Egasi (владелец), **A** — Administrator, **W** — Ishchi.

## A. Критическая бизнес-логика

### A1. Параметры рецепта (размер, толщина, выход партии)

| Пункт | Содержание |
|---|---|
| 1. В макете | Лист 2, «Рецепт»: `RCP-001`, Ўлчам `2000 × 600 мм`, Қалинлик `20 мм`, «Ҳосил бўладиган маҳсулот **1 дона**», ниже — состав на эту единицу |
| 2. Требует ТЗ | «программа проверяет рецепт товара… сколько сырья нужно по рецепту» — норма расхода должна относиться к **известной единице выхода** |
| 3. Есть в коде | `Recipe(product, name, description, is_active)`, `RecipeItem(material, quantity_required, unit)`; `get_recipe_requirements()` = `quantity_required × количество изделий` — то есть выход **жёстко равен 1** |
| 4. Не хватает | `code` (RCP-001), `size`, `thickness`, `output_quantity`; деления требования на выход партии |
| 5. Файлы | `apps/warehouse/models.py` (Recipe), `serializers.py` (RecipeSerializer), `apps/production/services.py::get_recipe_requirements`, `apps/orders/models.py::_recipe_requirements`, `static/js/components/finished_products.js` |
| 6. В БД | `Recipe.code` CharField(30), `size` CharField(100), `thickness` Decimal(6,2) мм, `output_quantity` Decimal(15,3) default 1, констрейнт `output_quantity > 0` |
| 7. Permissions | Чтение — все сотрудники (рабочему нужен состав); изменение — E/A (как сейчас) |
| 8. Regression tests | выход 2 → расход на изделие делится пополам; выход 1 → поведение не меняется (старые рецепты); `output_quantity = 0` отклоняется; нехватка считается по новому правилу; заказ показывает те же требования, что и подтверждение работы |
| 9. Риск | **Средний.** Формула расхода меняется. Митигация: default `output_quantity = 1` — для всех существующих рецептов расчёт остаётся прежним, тест это фиксирует |

### B3. Приход нескольких материалов одним документом

| Пункт | Содержание |

| 2. Требует ТЗ | «добавлять приход материала», «все изменения склада должны иметь историю» |
| 3. Есть в коде | `record_incoming()` — одна позиция за вызов; `document_number` дублируется в каждом движении строкой |
| 4. Не хватает | Модели документа прихода с позициями и атомарного проведения всех строк |
| 5. Файлы | новая модель в `apps/warehouse/models.py`, сервис `services.py::create_receipt`, вьюсет + сериализаторы, `static/js/components/warehouse.js` |
| 6. В БД | `GoodsReceipt(company, supplier, document_number, receipt_date, comment, created_by, created_at)` + `GoodsReceiptLine(receipt, material, quantity, price_per_unit)`; у `StockMovement` — FK `receipt` (null) для связи истории с документом |
| 7. Permissions | Создание — E/A; цену за единицу принимает и сохраняет **только E** (как в текущем `incoming`); чтение документа — E/A, суммы в ответе только E |
| 8. Regression tests | документ из 3 позиций меняет 3 остатка и создаёт 3 движения, связанных с одним документом; ошибка в одной позиции откатывает весь документ; администратор не видит цен в документе; параллельное проведение двух документов на один материал суммируется (PG) |
| 9. Риск | **Средний.** Существующий одиночный `incoming` **сохраняется** — новый документ реализуется рядом и переиспользует `record_incoming` внутри транзакции, поэтому старые сценарии и тесты не затрагиваются |

## Спорные пункты: анализ и рекомендация

### 1. Минимум фото («камида 1» / «камида 2»)

* Источник истины: **текст ТЗ** — там сказано «прикреплять фото результата», без минимума. Макет добавляет ограничение, причём **противоречиво**: лист 2 требует 1 снимок, лист 6 — 2.
* В коде правило намеренно мягкое, это зафиксировано комментарием: рабочий без камеры или со слабой связью не должен застревать.
* **Рекомендация:** сделать минимум **настройкой компании** (`min_work_photos`, по умолчанию 0). Владелец включает требование сам. Так закрывается и макет, и не ломается работа в цеху. Реализовывать — только после вашего «да».

### 2. Произвольные роли («+ Янги роль қўшиш»)

* Текст ТЗ: «Сделать три типа аккаунтов». Динамические роли ломают всю модель прав, включая серверную финансовую изоляцию.
* **Рекомендация:** оставить три роли. Кнопку из макета не реализовывать.

### 3. «Бугунги иш 18 соат»

* Оплата в ТЗ — строго за единицу продукции. Учёт часов ввёл бы вторую модель оплаты.
* **Рекомендация:** показывать не «отработанные часы», а **плановую загрузку по срокам задач на сегодня** (сумма плановых часов не нужна — достаточно числа задач и ближайшего срока). Либо убрать показатель. Минимально конфликтующий вариант — второй: убрать, а место отдать под «Вазифалар N та».

### 4. Резервные копии

* Платформенный backup владельцу не открывать (доступ к чужим tenant).
* **Рекомендация:** отдельный **экспорт данных своей компании** (по сути расширенный экспорт), без доступа к платформенным дампам, конфигурации и логам.
