## Что реально реализовано

### P2-1. Счётчики склада и агрегаты

**Семантика зафиксирована в тестах, а не в комментариях:**

| Показатель макета | Формула |
|---|---|
| «Материаллар 156» | число НЕархивных позиций материалов компании |
| «Турлари 28» | число РАЗНЫХ непустых `stone_type` среди них; незаполненный тип видом камня не считается |
| Чип «Оқ мрамор 250.75 м²» | сумма остатка по виду; при смешанных единицах внутри вида сумма = null, отдаётся разбивка |
| «Қиймати» | остаток × средняя себестоимость, **только владельцу** |

Перебор материалов в Python заменён одним SQL-агрегатом (`Case/When/Count`) с теми же
правилами, что у `RawMaterial.stock_severity`.

| Требование этапа | Тест |
|---|---|
| Уникальные типы | `test_counts_materials_and_distinct_types`, `test_empty_stone_type_is_not_a_type` |
| Общее количество | `test_counts_materials_and_distinct_types` |
| Агрегаты по единицам | `test_type_totals_sum_quantity_per_type`, `test_mixed_units_within_type_have_no_single_total` |
| Соответствие макету | значения из реальных строк, никаких констант |
| Tenant isolation | `test_other_company_materials_not_counted` |
| Архивные не считаются | `test_archived_excluded_from_all_counters` |
| Производительность | `test_summary_query_count_does_not_grow_with_data` — 6 запросов и на 30, и на 60 позициях |
| SQL == модель | `test_sql_severity_counters_match_model_property` |

Вкладки — серверный фильтр по `movement_type` поверх реальных `StockMovement`.
Категории: `incoming` = поставка; `outgoing` = расход + производство + брак;
`returned` = только возврат (в макете это отдельная колонка).

| Требование этапа | Тест |

| Қайтарилган | `test_returned_tab_is_separate_from_incoming` |
| Корректность mapping | те же четыре теста + `test_unknown_category_returns_nothing` |
| Итоги под таблицей | `test_totals_match_movements`, `test_totals_respect_filters`, `test_totals_are_not_page_limited` (61 движение при странице 50) |

### P2-3. Управление сессиями

**Архитектура изучена до реализации:** SimpleJWT, `ROTATE_REFRESH_TOKENS=True`,
`BLACKLIST_AFTER_ROTATION=True`, таблицы `OutstandingToken`/`BlacklistedToken`,
кастомный refresh с claim `fpr` (хеш отпечатка устройства).

**Параллельная auth-система НЕ вводилась:** источник истины прежний, отзыв — штатный
blacklist. Добавлена только таблица метаданных `UserSession` (jti, хеш отпечатка,
user-agent, IP): в `OutstandingToken` этих полей нет, а список устройств без них
нечитаем. Текущая сессия определяется по `fpr` из access-токена — экспериментально
подтверждено, что simplejwt копирует этот claim из refresh в access.

| Требование этапа | Тест |
|---|---|
| Просмотр активных сессий | `test_login_creates_visible_session`, `test_two_devices_two_sessions` |
| Определение устройства | `test_session_metadata_recorded` (отпечаток хранится хешем) |
| Отзыв конкретной сессии | `test_revoke_specific_session_kills_its_refresh` |
| Отзыв всех остальных | `test_revoke_others_keeps_current` |
| Обычный logout работает | `test_plain_logout_still_works`, `test_logout_removes_session_from_list` |
| Нельзя управлять чужими | `test_cannot_revoke_foreign_session`, `test_owner_cannot_revoke_employee_session`, `test_revoke_others_does_not_touch_other_users` |
| Tenant isolation | `test_only_own_sessions_visible` |
| SuperAdmin отдельно | `test_superadmin_sessions_are_separate` |
| Refresh после отзыва | `test_revoke_specific_session_kills_its_refresh` (401) |
| Access после отзыва | `test_access_token_survives_until_expiry_by_design` |
| Штатный механизм | `test_revocation_uses_standard_blacklist` |
| Отказоустойчивость | `test_session_visible_even_without_metadata` |

**Про access-токен честно:** отзыв немедленно убивает refresh; уже выданный access
живёт до истечения (45 минут) — это свойство stateless-JWT, а не недоработка.
Для мгновенной блокировки человека есть `is_active`, и тест проверяет оба поведения.
