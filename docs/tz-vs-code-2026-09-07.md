## 1. Короткий вердикт

Бэкенд закрывает ТЗ **примерно на 90 %**: модель данных, роли, разграничение финансов на уровне API,
производство с подтверждением, заказы, клиенты, расходы, оплата труда, аналитика владельца и админа,
квартальные отчёты, экспорт, чат, уведомления и требования безопасности — реализованы и покрыты тестами.

Основные расхождения не в бизнес-логике, а в трёх местах:

1. **Модель задачи (`Task`) беднее макета** — нет названия, описания, срока и вложения-чертежа.
2. **Складская топология из макета отсутствует** — нет справочника складов («Асосий омбор») и ячеек с
   занятостью («А-01 … А-08», «Банд 86.1 %»), есть только зона А/Б/В и текстовое место хранения.
3. **Локализация нарушена в двух точках**, хотя ТЗ формулирует это как жёсткое правило:
   серверные уведомления не переводятся, и в JS остались ~20 захардкоженных строк.

### 2.4 Готовая продукция

Все 11 полей ТЗ реализованы (`category`, `unit`, `quantity`, `photo`, `description`, `min_stock`,
`required_for_orders` как резерв, `cost_price`, `sale_price` — последние два только владельцу). ✅

### 2.5 Производство (режим с подтверждением)

Алгоритм из ТЗ (шаги 1–6) реализован **дословно**: `production/services.confirm_work` в одной транзакции
проверяет рецепт → проверяет сырьё → списывает → приходует готовое → начисляет оплату → пишет
`StockMovement` → двигает статус заказа; при отклонении склад и начисления не трогаются, работник получает
комментарий. Фото результата — `WorkRecord.photo` + отдельная модель `WorkPhoto` (несколько фото). ✅

⚠️ Макет требует «камида 1 та сурат» / «камида 2 та сурат» — **минимального количества фото на сервере
нет**, поле необязательное.

### 2.7 Заказы

10 статусов ТЗ — совпадают со `Order.Status` один в один. Поля (клиент, товар, количество, единица, срок,
работник, комментарий, фото/чертёж, статус, статус оплаты) — есть. Автопроверка наличия готового товара,
расчёт «сколько произвести», разузлование по рецепту, нехватка сырья и красная карточка — реализованы
(`shortage_quantity`, `material_shortage`). ✅

⚠️ Поле «Материал» в заказе ТЗ трактует как атрибут заказа; в коде материал выводится из рецепта товара.
Для макета «Буюртма тафсилоти» (список требуемых материалов с «Етарли / Материал етарли эмас») этого
достаточно, но у заказа со свободным названием (`custom_product_name`) рецепта нет → список материалов пуст.

### 2.9 Расходы

18 категорий ТЗ — **совпадают полностью**, включая «личный вывод средств владельцем», «долги работников»,
«возвраты клиентам». Поля: дата, категория, сумма, комментарий, фото чека, кто добавил, способ оплаты — все есть. ✅

### 2.10 Оплата работников

`LaborRate(product, operation, rate_per_unit, unit)`, начислено = количество × ставка. ✅
Операции: кесиш, сийлаш (полировка), монтаж, қутлаш, бошқа — примеры ТЗ (резка/полировка/изделие/монтаж) покрыты.
Работник видит только свой заработок, админ — только количество, владелец — суммы. ✅

### 2.11 Аналитика владельца

Все 17 показателей ТЗ присутствуют в `OwnerAnalyticsData` (выручка, себестоимость, валовая прибыль, расходы,
зарплаты, налоги, потери, долги клиентов, долги работников, вывод владельца, чистая прибыль, касса, остатки,
заказы, топ-товары, самый активный работник). Периоды: сегодня/вчера/неделя/месяц/квартал/год/свой — ✅.
Формулы совпадают с ТЗ (проверено построчно в `reports/services.get_period_financials`).

⚠️ Единственное расхождение: **топ-товары ранжируются суммой количеств разных единиц** (шт + м² в одном рейтинге).

### 2.12 Аналитика администратора

Все 9 показателей ТЗ есть в `get_admin_operational_analytics`, суммы отсутствуют (неоплатившие клиенты
отдаются только `id + name`). ✅

### 2.14 Чат и уведомления

Матрица «кто кому пишет» из ТЗ реализована (`can_write_to_owner` для работника). ✅
Уведомления: **все типы из ТЗ есть** (новый заказ, новый расход, клиент не оплатил, просрочен долг, отказ

отправляет «в никуда».

### 2.15 Безопасность

Все 8 требований ТЗ выполнены и перевыполнены: аккаунты создаёт только владелец (плюс делегирование админу),
пароли в hash, RBAC, финансы не уходят в API админу/работнику, `audit_logs` на все действия, склад меняется
только после подтверждения, вместо удаления — архивирование, история склада полная.
Сверх ТЗ: 2FA (TOTP + резервные коды), одноразовые Access-Key, привязка refresh-токена к устройству, CSP,
троттлинг, бэкапы. ✅

⚠️ Макет «Хавфсизлик ва захира нусха» показывает пункт **«Сеансларни бошқариш» (активные сессии)** — в API
такого эндпоинта нет (есть только глобальный разлогин через blacklist).

### 4.2 Уведомления и отчёты не переводятся

Тексты уведомлений формируются строками в `apps/*/services.py` (узбекский в бизнес-событиях, русский в
подписках), язык получателя (`User.language`) не используется. Заголовки колонок PDF/Excel — тоже в коде.
ТЗ требует перевода уведомлений и отчётов явно.

### 4.3 Роль `manager` вне ТЗ

Пятая роль в ТЗ не описана. Либо её узаконить (дополнить ТЗ), либо убрать — сейчас у неё свой набор прав,
который никем не проверяется по спецификации.

### 4.4 Дефекты, найденные ранее (актуальны и для ТЗ)

* Вложения в чате не работают (макеты 3 и 9 их показывают).
* Итог долгов на экране клиентов = `NaN`, считается только по первой странице.
* Два разных правила потолка зарплаты (сериализатор vs view).
* Два параллельных движка подписок (`companies` + `billing`).

## 5. Противоречия и вопросы, которые надо снять до реализации

1. **Единицы измерения.** ТЗ: 4 единицы. Код: 7 (`dona` = «шт» по-узбекски, дубль `sht`; плюс кг и м³, которые
   реально нужны для клея/полиэстера из макета 2). Нужен финальный список и правило миграции существующих данных.
2. **«Материал» в заказе.** Атрибут заказа или всегда через рецепт? От этого зависит экран «Буюртма тафсилоти»
   для заказов со свободным названием товара.
3. **Задача vs заказ.** Макет показывает задачу как самостоятельный документ (название, описание, срок, чертёж).
   Считаем ли задачу отдельной сущностью с собственным сроком, или это «вид» заказа?
4. **Склады и ячейки.** Нужен ли полноценный справочник складов и ячеек с площадью/занятостью (макет 1) или
   достаточно текущей зоны А/Б/В?
5. **Просрочка долга.** По какому событию считать «муддати ўтган»: срок заказа, дата выдачи + N дней, или
   отдельное поле «срок оплаты» в заказе?
6. **Статус качества материала** («Аъло/Яхши/Қуйида/Критик»): это состояние партии (качество) или уровень
   остатка? На макете значения смешаны.
7. **Отдельные экраны vs вкладки.** Делать 21 экран владельца буквально (и разную нижнюю навигацию по ролям,
   как на макетах) или оставить текущую группировку по вкладкам?

## 6. Предлагаемый порядок работ (когда дадите добро)

**Спринт 1 — привести в соответствие обещанное (без новых сущностей)**
1. Вложения в чате: поле + сериализатор + валидация + отдача URL.
2. Итоги долгов: серверный агрегат вместо клиентского `reduce`.
3. Вынести 20+ захардкоженных строк в `uz_cyrl.json`/`ru.json` + линт-проверка «нет кириллицы в JS»
   (можно вынести в CI, чтобы правило ТЗ не нарушалось снова).
4. Локализация уведомлений: шаблоны по ключам + язык получателя; локализация заголовков PDF/Excel.
