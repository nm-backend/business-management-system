# Adversarial-аудит на PostgreSQL — SkladPro.Nod

Дата: 2026-09-08. Задача: враждебно проверить пункты, оставшиеся «за рамками»,
с главным приоритетом — настоящий PostgreSQL.

## Стенд

| Параметр | Значение |
|---|---|
| СУБД | **PostgreSQL 16.2** (пакет `pgserver`, реальные бинарники, не эмуляция) |
| Подключение | TCP `127.0.0.1:5432`, драйвер `psycopg2`, движок `django.db.backends.postgresql` |
| Настройки | `pg_settings.py` — импортирует боевой `skladpro/settings/base.py` как есть, подменяются только координаты БД |
| БД | создана с нуля (`CREATE DATABASE skladpro`), все ~200 миграций применены последовательно |
| Идемпотентность миграций | повторный `migrate` → «No migrations to apply» |

Воспроизвести: поднять postgres на 5432, затем
`.venv/bin/python manage.py test --settings=pg_settings`
(файл `pg_settings.py` в репозиторий не коммитится — это конфиг стенда).

## Итог прогонов

| Прогон | Результат |
|---|---|
| Полный backend на PostgreSQL | **1280 тестов, OK, 2 пропуска** |
| Полный backend на SQLite | 1280 тестов, OK, 37 пропусков (PG-only сценарии) |
| Frontend (vitest) | 82 теста, OK |

На sqlite пропускается 35 сценариев, которые на PostgreSQL реально выполняются
(гонки + часть проверок движка) — это и есть цена «зелёного» sqlite-прогона.

## Что подтверждено на PostgreSQL

* Все ~200 миграций с нуля + идемпотентность.
* Полный backend-suite: **1280 тестов**.
* Все сценарии конкурентности (18 тестов, до 8 потоков на строку).
* Тип `numeric` у денежных колонок и отсутствие двоичного дрейфа.
* Квартальные отчёты обоих видов, изоляция компаний, экспорты, JWT.
* **Обвязка гонок проверена отдельно**: 4 потока × `pg_sleep(0.4)` = 0.41 c
  (4 разных backend PID), а `select_for_update` заставил второй поток ждать
  0.5 c — значит параллелизм настоящий, а зелёные тесты не «ни о чём».

## Что подтверждено только на SQLite

Ничего критичного: тот же набор из 1280 тестов проходит на обоих движках,
разница только в 35 пропусках на sqlite (PG-only сценарии гонок). То есть
sqlite-прогон — подмножество, а не отдельная область доверия.

## Что ещё не реализовано

| Пункт | Состояние |
|---|---|
| Отдельный срок оплаты долга и бакеты просрочки (15/10/7 дней) | просрочка считается по `Order.deadline`; отдельного `payment_due_date` и группировки «Муддати ўтган / Қарзи бор / Қарзи йўқ» нет |
| Справочник поставщиков | `supplier` — строка; нет модели, истории цен и связи с приходами |
| Тип клиента и ответственный сотрудник | полей нет |
| Параметры рецепта (размер, толщина, выход партии) | выход всегда 1, габариты не хранятся |
| Управление активными сессиями | список устройств/сессий пользователю не показывается |
| Параметры экспорта («включить графики/пояснения», детализация) | экспорт без параметров |
| Отдельные SPA-экраны из списка ТЗ (21 у владельца) | данные доступны, но разложены по вкладкам, а не по отдельным маршрутам |

## Что требует отдельного решения (нужен ваш выбор)

1. **Срок оплаты.** Ввести `Order.payment_due_date` (отдельно от срока
   изготовления) или считать просрочку по `deadline`, как сейчас? Первое —
   миграция + правки отчётов и уведомлений, второе — оставить как есть.
2. **Поставщики.** Полноценный справочник (модель, привязка приходов,
   история цен) меняет форму приёма материала и импорт исторических данных.
3. **Управление сессиями.** Нужен реестр выданных refresh-токенов с
   устройством и IP; сейчас отзыв работает, но списка «где я вошёл» нет.
4. **PostgreSQL в CI.** Стенд поднимался вручную; чтобы PG-прогон был
   обязательным, нужен сервис postgres в пайплайне (и решение, гонять ли
   18 многопоточных тестов на каждом коммите — они добавляют ~9 c).
5. **Нагрузочное тестирование.** Проверена корректность под конкуренцией, но
   не пропускная способность: sustained-нагрузка и пулы соединений — отдельная
   задача с отдельным стендом.
